networking off, pre-commit hooks, and a CI pipeline that runs exactly what a
developer runs locally.

is what keeps Phase 6's dbt models and Phase 3's parsers honest — and it closes
the compliance requirements (no secrets, no payloads, no live-network tests)
before there is any data to leak.
Output: a green pipeline that a developer can reproduce exactly on their machine.

<task type="auto">
  <name>Task 4: Repository hygiene guards</name>
  <files>scripts/check_no_payloads.py, .pre-commit-config.yaml</files>
  <read_first>.gitignore, CLAUDE.md</read_first>
  <action>
`scripts/check_no_payloads.py` inspects the staged (or, in CI, changed) file
list and fails on: any `.env` other than `.env.example`; files matching
`*.parquet`, `*.duckdb`, `*.sql.gz`, `*.dump`; anything under `data/` or
`exports/`; any file over a size threshold (default 1 MB) not on a small
allowlist. This implements REQ-24 — it is the mechanical backstop that stops a
scraped payload from being committed and redistributed.

`.pre-commit-config.yaml` wires: ruff (lint + format), a `detect-private-key`
hook, `check-added-large-files`, `end-of-file-fixer`, `trailing-whitespace`,
`check-yaml`, `check-toml`, plus `check_no_payloads.py` as a local hook.

Note in the config that pre-commit is a convenience, not the enforcement — CI is
the enforcement, because hooks can be bypassed with `--no-verify`.
  </action>
  <verify>uv run pre-commit run --all-files &amp;&amp; uv run python scripts/check_no_payloads.py</verify>
  <acceptance_criteria>
    - check_no_payloads.py exits non-zero for a staged .env and for a staged .parquet
    - .env.example is explicitly allowed
    - pre-commit config includes detect-private-key
  </acceptance_criteria>
  <done>Hooks pass on a clean tree and reject secrets, payloads and oversized files.</done>
</task>

<task type="auto">

  <files>.github/workflows/ci.yml, Makefile</files>
  <read_first>Makefile, scripts/check_licenses.py, scripts/check_no_payloads.py</read_first>
  <action>
Give the `test` and `lint` Makefile targets stubbed in 01-02 their real bodies,
and add `test-integration`.

CI workflow on push and pull request:
- `lint` job — checkout, install uv, `make lint`
- `test` job — checkout, install uv, `make test` (unit only, no services)
- `integration` job — a `postgres:16` service container, `make migrate` then
  `make test-integration`
- `compliance` job — `scripts/check_no_payloads.py`, `scripts/check_licenses.py`
  (from 01-04), and a secret scan

Per D-16 and REQ-29, CI must invoke the Makefile targets, not a parallel list of
inline commands. The moment CI has its own command list, local green and CI
green stop meaning the same thing — which is the exact failure this requirement
exists to prevent.

Pin action versions to a major tag and cache the uv environment on the lockfile
hash.
  </action>
  <verify>make lint &amp;&amp; make test &amp;&amp; make test-integration</verify>
  <acceptance_criteria>
    - ci.yml contains 'make lint' and 'make test'
    - ci.yml contains no direct 'ruff'/'mypy'/'pytest' invocation
    - The compliance job runs both check scripts
    - The integration job declares a postgres service
  </acceptance_criteria>
  <done>All four CI jobs pass, running the same commands available locally.</done>
