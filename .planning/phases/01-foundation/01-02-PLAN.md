setup story.

later phase assumes that promise holds.

<task type="auto">
  <name>Task 1: Multi-stage Dockerfile</name>
  <files>docker/Dockerfile, docker/entrypoint.sh</files>
  <read_first>pyproject.toml, .planning/phases/01-foundation/01-CONTEXT.md</read_first>
  <action>
Builder stage on `python:3.12-slim`: install `uv`, copy `pyproject.toml` and
`uv.lock` **before** the source, run `uv sync --frozen --no-dev` into `/opt/venv`.
Copying the lockfile first is what makes the dependency layer cacheable — copying
source first rebuilds the world on every code change.

Runtime stage on `python:3.12-slim`: copy `/opt/venv`, copy `src/`, create a
non-root `emeye` user, `WORKDIR /app`, `ENV PATH=/opt/venv/bin:$PATH`,
`PYTHONUNBUFFERED=1`. Default command `emeye --help`.

`docker/entrypoint.sh` waits for Postgres to accept connections before exec'ing
the given command, with a bounded timeout and a clear error if it expires. Do
not busy-loop forever — a hung container that never explains itself is worse
than a failed one.

Per D-03 this single image serves app, scheduler, Streamlit and Jupyter; only
the command differs. Do not create a second image.
  </action>
  <verify>docker build -f docker/Dockerfile -t emeye:dev . &amp;&amp; docker run --rm emeye:dev emeye --version</verify>
  <acceptance_criteria>
    - Dockerfile has exactly two FROM lines (builder + runtime)
    - pyproject.toml and uv.lock are copied before src/
    - Runtime stage contains a USER instruction naming a non-root user
    - entrypoint.sh has a bounded wait, not an infinite loop
  </acceptance_criteria>
  <done>The image builds and `emeye --version` runs inside it as a non-root user.</done>
</task>

`compose.yaml` with two services for this phase:

- `postgres`: `postgres:16`, named volume `pgdata` at
  `/var/lib/postgresql/data`, healthcheck using `pg_isready`, credentials from
  `.env`. Bind the port to `127.0.0.1` only — this is a personal warehouse and

- `app`: built from `docker/Dockerfile`, `depends_on` postgres with

`src/emeye/config.py` defines, each with a comment explaining what it does and
what a sensible local value is. Required-with-no-default variables must be

needs, and note where the two naming schemes overlap.

`EMEYE_USER_AGENT` gets an explicit comment: it must carry a real contact
address, because that is the honest-identification obligation from CLAUDE.md,
not a formality.

<task type="auto">
  <name>Task 4: Makefile as the only interface</name>
  <files>Makefile</files>
  <read_first>compose.yaml, CLAUDE.md</read_first>
  <action>
Targets, all routed through `docker compose` so nothing needs a host-level
Python: `up`, `down`, `build`, `migrate`, `revision` (autogenerate, takes a
message), `shell` (bash in app), `psql`, `logs`, `test`, `lint`, `clean`.

`make help` is the default goal and self-documents from `##` comments on each
target.

Bootstrap protection: if `.env` is missing, `make up` copies `.env.example` to
`.env` and stops with a message telling the user which values to fill in. It
must not start with placeholder credentials and pretend that worked.

`test` and `lint` are declared here and given their real bodies in 01-03 — leave
them as documented stubs that fail with a pointer rather than silently passing.
A no-op `make test` that exits 0 is the most dangerous target in this file.
  </action>
  <verify>make help &amp;&amp; make up &amp;&amp; make migrate &amp;&amp; make down</verify>
  <acceptance_criteria>
    - `make help` lists every target with a description
    - No target invokes python, uv, alembic or psql on the host
    - Missing .env halts `make up` with an actionable message
    - Stub test/lint targets exit non-zero
  </acceptance_criteria>
  <done>The documented workflow runs end to end with only Docker installed.</done>
