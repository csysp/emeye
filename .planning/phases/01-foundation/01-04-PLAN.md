<objective>
Choose and apply a strong protective license, then make dependency license
compatibility a standing, automated check rather than a one-time review.

Purpose: licensing is governance, not paperwork. It determines whether someone
can take this work, build a commercial service on it, and give nothing back —
and it constrains which libraries the project can ever use. Deciding it in
Phase 1 is far cheaper than deciding it after eight phases of code exist.
Output: a licensed repository, a written rationale, and a CI-enforced
dependency license inventory.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>Which strong protective license does emeye adopt?</decision>
  <context>
This is the one decision in Phase 1 that is genuinely hard to walk back.
Relicensing later requires the agreement of every copyright holder, and any copy
someone already received under the old terms stays usable under those terms
forever. While you remain the sole author the practical cost of changing your
mind is low — it hardens the moment anyone else contributes or forks.

Two facts shape the choice for this specific project:

1. **emeye is network-deployable.** Phase 8 adds a Streamlit UI. Under a plain
   GPL, someone may modify emeye, run it as a hosted service, and never publish
   their changes — distribution never occurs, so the copyleft never triggers.
   The AGPL's section 13 closes exactly that gap.
2. **Essentia is AGPL-3.0.** The deferred audio ground-truth work (the only way
   to audit how wrong vendor BPM and key values are) points at Essentia. An AGPL
   project can use it; a permissive or non-OSI source-available project cannot,
   without buying a commercial license.

Dependency compatibility is not a differentiator between the copyleft options —
the stack is MIT/BSD/Apache-2.0, all of which flow into GPL-3.0 or AGPL-3.0
work. One item to confirm in Task 3: `psycopg` is LGPL-3.0, which is compatible
with AGPL/GPL-3.0, but carries relinking obligations that need review under any
non-OSI option.
  </context>
  <options>
    <option id="agpl-3.0-or-later">
      <name>AGPL-3.0-or-later (recommended)</name>
      <pros>Strongest protection available in an OSI-approved license. Closes the hosted-service loophole that matters for a project with a web UI. Keeps Essentia (AGPL-3.0) available for the deferred audio validation work. Compatible with the entire current dependency stack. Universally recognised, so its meaning is not in dispute. The "-or-later" suffix lets the project inherit future FSF fixes without a relicensing exercise.</pros>
      <cons>Deters some commercial adoption and contribution, which is the point but is still a cost. Some organisations ban AGPL dependencies outright. Cannot be combined into proprietary work — irrelevant for a personal tool, relevant if you ever want to sell a closed derivative yourself.</cons>
    </option>
    <option id="gpl-3.0-or-later">
      <name>GPL-3.0-or-later</name>
      <pros>Strong copyleft on distribution, and marginally more palatable to organisations with blanket AGPL bans. Same dependency compatibility as AGPL.</pros>
      <cons>Leaves the hosted-service loophole wide open — for a project whose main surface is a web app, this is the specific weakness you would be choosing to accept. Weaker than the alternative at no meaningful benefit for a personal tool.</cons>
    </option>
    <option id="source-available-noncommercial">
      <name>Source-available non-commercial (PolyForm Noncommercial 1.0.0 or BUSL-1.1)</name>
      <pros>Directly forbids commercial use, which is a blunter and in some readings stronger protection than copyleft. BUSL adds a change date after which the code converts to an open license.</pros>
      <cons>Not open source and not OSI-approved — GitHub will not label it, and most contributors and packagers will avoid it. Forecloses Essentia and any other AGPL dependency. Raises the LGPL relinking question for psycopg. "Non-commercial" is famously ambiguous to enforce, and enforcement is yours alone. Strictly more legal surface than a personal analytics tool warrants.</cons>
    </option>
  </options>
  <resume-signal>Select: agpl-3.0-or-later, gpl-3.0-or-later, or source-available-noncommercial</resume-signal>
</task>

<task type="auto">
  <name>Task 2: Apply the chosen license across every surface in one pass</name>
  <files>LICENSE, README.md, pyproject.toml, docs/LICENSING.md, src/emeye/**/*.py</files>
  <read_first>.planning/phases/01-foundation/01-CONTEXT.md</read_first>
  <action>
Using the license selected at the checkpoint (referred to below as `<SPDX>`):

1. `LICENSE` — the **complete, unmodified** upstream text. Do not summarise it,
   do not reflow it, do not edit the boilerplate instructions out of the GNU
   licenses' appendix. A modified license text is a different license.
2. `pyproject.toml` — set `license = { text = "<SPDX>" }` (or the SPDX expression
   form supported by the build backend in use) and add the matching
   `License ::` classifier. This fills the gap plan 01-01 deliberately left.
3. `README.md` — replace the existing "## Legal" section body with a statement
   naming `<SPDX>`, linking `LICENSE`, and adding a one-line plain-English
   summary of what it obliges a redistributor to do. Keep the existing
   personal-use / polite-collection language; it addresses a different concern
   (how emeye treats *other people's* data) and both statements need to coexist.
4. Source headers — add `# SPDX-License-Identifier: <SPDX>` as the first line of
   every `.py` file under `src/`. Add it to the file template expectations in
   `CLAUDE.md` so later phases keep the convention.
5. If a GNU license was chosen, add the standard copyright-and-warranty notice
   block to `src/emeye/cli/main.py` and surface it via `emeye --version`.

Consistency is the whole point of doing this in one task: a `LICENSE` that says
one thing and packaging metadata that says another creates genuine ambiguity
about which terms actually apply.
  </action>
  <verify>test -s LICENSE &amp;&amp; grep -rL "SPDX-License-Identifier" src --include="*.py"</verify>
  <acceptance_criteria>
    - LICENSE is non-empty and byte-identical to the upstream text for the chosen license
    - pyproject.toml names the same SPDX identifier as LICENSE
    - Every .py file under src/ carries an SPDX-License-Identifier header
    - README's Legal section names the license AND retains the data-collection language
  </acceptance_criteria>
  <done>Four surfaces (LICENSE, packaging, README, headers) all name the same license; nothing disagrees.</done>
</task>

<task type="auto">
  <name>Task 4: Make compatibility a standing check</name>
  <files>scripts/check_licenses.py, docs/LICENSING.md</files>
  <read_first>docs/licenses/THIRD-PARTY.md</read_first>
  <action>
Write `scripts/check_licenses.py` that walks the resolved runtime dependencies
and exits non-zero when it finds a license outside an allowlist appropriate to
the chosen project license, or a license it cannot identify.

Ship an explicit `ALLOWED` set (MIT, BSD-2/3-Clause, Apache-2.0, ISC, PSF,
LGPL-3.0, MPL-2.0, plus GPL-3.0/AGPL-3.0 if the project is itself AGPL) and an
`EXCEPTIONS` mapping keyed by package name, where every entry carries a written
justification. An exception without a reason is not an exception, it is a
silenced alarm.

Write `docs/LICENSING.md` capturing: the decision, the reasoning from the
checkpoint, what the license obliges a redistributor to do, the allowlist and
its rationale, how to regenerate the inventory, and what to do when a new
dependency fails the check.

Note in the file that plan 01-03 wires this script into CI — this plan produces
the check, 01-03 enforces it on every push.
  </action>
  <verify>uv run python scripts/check_licenses.py</verify>
