The job contract, run tracking, the reparse path, `emeye status`, and the
scheduler that will eventually run the collectors.

Purpose: this is what makes ingestion operable rather than merely possible. A
collection system whose health you cannot see is one you will silently stop
trusting — and given the prime directive, a gap you notice six months late is
six months of chart data you never captured.
Output: a runnable, observable, idempotent job substrate.

`base.py` defines an abstract `IngestJob`:
- class attributes `source: str`, `job_name: str`
- `run(context) -> JobResult` where `JobResult` carries `items_fetched`,
  `items_written`, `cache_hits`, `cache_misses`
- a `JobContext` giving the job its settings, a `PoliteClient` for its source,
  and the bronze store

The job does **not** touch `ingest_run` (D-13). The runner owns that
bookkeeping, so a job physically cannot forget to record itself.

`registry.py` maps `"<source>.<job_name>"` to job classes via an explicit
registration decorator. Explicit over import-scanning: a job that fails to
import should be a loud error at startup, not a job that silently does not exist.

Phase 2 registers one job — a `demo` source used only by tests — so the
substrate is exercised without any real upstream. Delete it in Phase 3 or keep
it as a fixture; either is fine, but it must never be enabled by default.
  </action>

<task type="auto">
  <name>Task 2: The runner</name>
  <files>src/emeye/jobs/runner.py</files>
  <read_first>src/emeye/jobs/base.py, src/emeye/db/models.py</read_first>
  <action>
`run_job(key, **params) -> IngestRun` does the bookkeeping:

1. Resolve the job; refuse if its source is disabled (`SourceDisabled`), and
   record nothing — a disabled source produces no run row, because it did not run.
2. Insert `ingest_run` with status `started` **before** calling the job (D-15),
   and commit it. A crashed process must leave a `started` row rather than no
   evidence at all: silence is indistinguishable from "never scheduled".
3. Call `run()`. On success, update to `succeeded` with counts and duration.
   If the job reports zero fetches because everything was cached, record
   `skipped_cache` instead — this is how the "one fetch per chart per reset"
   invariant gets *proved* rather than assumed (D-14).
4. On exception: update to `failed` with `error_type`, `error_message` and
   `traceback`, then re-raise. Never swallow (CLAUDE.md). The status update must
   happen in its own transaction so it survives the failure that caused it —
   a failure record rolled back with the failing work is worse than useless.
5. Log start and finish with source, job, status, counts and duration.

Add `find_stale_runs(older_than)` returning `started` rows past a threshold, for
`emeye status` to flag.
  </action>
  <verify>uv run pytest tests/unit/test_job_runner.py -q</verify>
  <acceptance_criteria>
    - The started row is committed before the job body runs
    - A failing job produces a failed row AND re-raises
    - The failure record survives in its own transaction
    - A fully-cached run records skipped_cache
  </acceptance_criteria>
  <done>Every run is recorded, including the ones that crash.</done>
</task>

  <read_first>src/emeye/cli/groups.py, src/emeye/jobs/runner.py</read_first>
  <action>
Replace the `ingest` and `status` stubs registered in `groups.py`.

`emeye ingest run <source>.<job>` — runs one job.
`emeye ingest list` — lists registered jobs and whether each source is enabled.
`emeye ingest reparse <source>` — rebuilds from bronze **without any network
access** (D-18, REQ-02). This is the phase's most important guarantee: it makes
a wrong parser a cheap mistake instead of lost data. It must not construct a
`PoliteClient` at all.

`emeye status` — a Rich table per source: last run time, status, items, cache
hit rate, duration, and the last error if any. Flag stale `started` rows
explicitly as suspicious rather than rendering them as if they were fine.
Exit non-zero if any source's most recent run failed, so cron mail and a
future healthcheck have something to key on.
  </action>

  <acceptance_criteria>

    - reparse contains no client construction
    - status exits non-zero when the latest run failed
    - status marks stale started rows as suspicious
  </acceptance_criteria>
  <done>The three commands work against a live warehouse.</done>

  <files>docker/crontab, compose.yaml</files>
  <read_first>compose.yaml, docker/Dockerfile</read_first>
  <action>
Add a `scheduler` service using the same image, differing only in command
(D-19). It runs cron, which invokes `emeye ingest run ...` on a schedule read
from `docker/crontab`.

Put it behind a **compose profile** (D-20) so `make up` on a workstation does
not silently begin collecting. Deployment enables it deliberately with
`--profile scheduler`. Document that in the README deployment section.

Phase 2 ships the mechanism with no real jobs scheduled — a commented example
only. Phase 3 adds the actual chart entries.

cron's environment is famously empty: pass the `EMEYE_*` variables explicitly
and send output to stdout so `docker compose logs` shows it, rather than to
cron's mail spool where nobody will look.
  </action>

    - crontab output goes to stdout
